# PRD: 外卖运营 Agent 本地测试 Demo

版本: v0.1  
日期: 2026-06-01  
项目代号: `food-ops-demo`

## 1. 背景

外卖平台商家后台存在大量重复运营动作，例如菜品改价、上下架、替换产品图、修改营业时间、调整联系电话、设置基础活动等。实际平台往往不提供完整 API，或 API 权限难以获取，因此需要一套在无真实 API、无真实商家后台前提下也能先验证的本地测试系统。

本项目先实现一个本地 Demo，用于验证核心链路:

```text
自然语言指令 -> 标准操作计划 -> 风险校验 -> 审批确认 -> Fake 执行 -> 回读校验 -> 审计留痕
```

第一版不接真实美团、饿了么、抖音后台，不引入真实浏览器 RPA，只通过 FakeAdapter 和本地 Mock 数据验证产品闭环。

## 2. 产品目标

### 2.1 MVP 目标

- 运营可以输入自然语言指令，例如: "把人民广场店的招牌牛肉饭改成 29.9"。
- 系统可以解析指令，生成结构化 `OperationPlan`。
- 系统可以展示变更预览，包括门店、菜品、当前价格、目标价格、风险等级。
- 中高风险操作必须经过人工确认。
- 确认后由 FakeAdapter 模拟执行。
- 执行后系统回读 Mock 数据，确认结果是否生效。
- 前端展示完整任务状态时间线。
- 系统保存审计记录，包含操作前后快照、执行结果、失败原因。

### 2.2 非目标

- 不接入真实外卖平台后台。
- 不处理真实登录态、二维码、短信验证码。
- 不接入 Playwright 或真实浏览器自动化。
- 不实现多租户 SaaS、权限矩阵、复杂审批流。
- 不支持真实批量跨平台改价。
- 不处理真实图片上传审核和活动规则审核。

## 3. 目标用户

### 3.1 运营人员

负责日常外卖门店维护，希望通过自然语言快速完成标准操作。

核心诉求:

- 不想逐个平台手动找入口。
- 希望先看到变更预览再执行。
- 希望知道任务执行到哪一步。
- 出错时能看懂原因。

### 3.2 运营主管

负责审批价格、活动、营业时间等高风险操作。

核心诉求:

- 能看到变更前后对比。
- 能判断风险等级。
- 能追踪是谁发起、谁确认、结果如何。

### 3.3 开发/产品验证人员

负责验证 Agent + 工作流 + RPA 架构是否可行。

核心诉求:

- 没有真实后台也能跑通闭环。
- 业务模块和平台执行器解耦。
- 后续能替换为 MockWebAdapter 或 RealRpaAdapter。

## 4. 用户场景

### 场景 1: 单菜品改价

用户输入:

```text
把人民广场店的招牌牛肉饭改成 29.9
```

系统输出:

```text
操作类型: 菜品改价
门店: 人民广场店
菜品: 招牌牛肉饭
当前价格: 32.00
目标价格: 29.90
风险等级: 中
需要确认: 是
```

用户点击确认后，系统执行并显示:

```text
任务状态: 成功
回读价格: 29.90
审计结果: 32.00 -> 29.90
```

### 场景 2: 菜品上下架

用户输入:

```text
把人民广场店的可乐下架
```

系统生成计划并要求确认。确认后 FakeAdapter 将该菜品状态从 `on_sale` 改为 `off_sale`，回读后展示执行成功。

### 场景 3: 营业时间修改

用户输入:

```text
把人民广场店明天营业时间改成 10 点到 21 点
```

系统生成营业时间修改计划，标记为高风险，必须确认后执行。第一版仅模拟长期营业时间修改，不处理节假日、特殊日期、多时间段冲突。

### 场景 4: 登录失效模拟

用户点击 "模拟登录失效" 或输入触发类指令后，任务进入 `manual_required` 状态。前端展示人工介入面板，用户点击 "模拟已处理"，任务继续执行。

## 5. 功能需求

### 5.1 自然语言解析

第一版使用本地规则解析，不调用真实 LLM。

必须支持:

- 门店名识别: 如 `人民广场店`
- 菜品名识别: 如 `招牌牛肉饭`、`可乐`
- 价格识别: 如 `29.9`、`29.90`
- 操作类型识别:
  - `menu.update_price`
  - `menu.update_sale_status`
  - `store.update_business_hours`
- 无法识别时返回明确错误，而不是生成不完整计划。

### 5.2 标准操作计划

系统生成 `OperationPlan`，核心字段包括:

```json
{
  "id": "plan_xxx",
  "operation_type": "menu.update_price",
  "store_name": "人民广场店",
  "target_name": "招牌牛肉饭",
  "changes": {
    "price": "29.90"
  },
  "risk_level": "medium",
  "requires_approval": true
}
```

### 5.3 风险校验

第一版风险规则:

- 查询类: 低风险。
- 单菜品改价: 中风险，需要确认。
- 菜品上下架: 中风险，需要确认。
- 营业时间修改: 高风险，需要确认。
- 价格低于 1 元: 拒绝执行。
- 价格变化超过 50%: 高风险。
- 找不到门店或菜品: 返回错误。
- 同名菜品多于 1 个: 进入人工选择或失败状态，第一版可直接返回 `target_ambiguous`。

### 5.4 审批确认

Demo 第一版不做多角色审批，只做本地确认按钮。

状态流转:

```text
previewed -> awaiting_approval -> queued -> executing -> verifying -> succeeded
```

用户未确认前，不允许执行。

### 5.5 FakeAdapter 执行

FakeAdapter 使用本地内存或 JSON 数据模拟平台后台。

必须支持:

- 获取门店快照。
- 查询菜品。
- 修改菜品价格。
- 修改菜品销售状态。
- 修改营业时间。
- 执行后回读数据。
- 模拟失败场景:
  - 登录失效
  - 目标不存在
  - 权限不足
  - 保存失败

### 5.6 任务状态时间线

前端展示任务状态:

```text
created
parsed
validated
previewed
awaiting_approval
queued
executing
verifying
succeeded
failed
manual_required
```

每个状态展示:

- 时间
- 状态名称
- 简短说明
- 错误码，若有

### 5.7 人工介入模拟

第一版只做模拟，不接真实二维码或远程浏览器。

前端提供:

- "模拟登录失效"
- "模拟二维码验证"
- "我已处理，继续执行"
- "取消任务"

后端状态进入:

```text
manual_required
```

用户点击继续后，任务进入:

```text
executing
```

### 5.8 审计日志

每次任务执行后记录:

- 指令原文
- 结构化计划
- 操作前快照
- 操作后快照
- 状态时间线
- 是否人工确认
- 是否人工介入
- 执行结果
- 失败原因

第一版审计可以保存在 `data/demo/audit.jsonl`。

- 审批确认按钮
- 任务状态时间线

## 7. 接口需求

### 7.1 健康检查

```http
GET /health
```

返回:

```json
{"status": "ok"}
```

### 7.2 获取 Mock 快照

```http
GET /api/demo/snapshot
```

返回门店、菜品、营业时间。

### 7.3 解析指令

```http
POST /api/demo/parse
```

请求:

```json
{"text": "把人民广场店的招牌牛肉饭改成 29.9"}
```

返回:

```json
{
  "plan": {},
  "preview": {},
  "errors": []
}
```

### 7.4 创建任务

```http
POST /api/demo/tasks
```

请求:

```json
{"plan": {}}
```

返回任务详情。

### 7.5 确认并执行

```http
POST /api/demo/tasks/{task_id}/confirm
```

返回执行后的任务状态。

### 7.6 模拟人工介入

```http
POST /api/demo/tasks/{task_id}/simulate-intervention
```

请求:

```json
{"type": "login_expired"}
```

### 7.7 继续任务

```http
POST /api/demo/tasks/{task_id}/resume
```

用于人工处理后继续执行。

## 9. 验收标准

### 9.1 基础验收

- 启动后访问 `http://127.0.0.1:8765` 能看到 Demo 页面。
- `GET /health` 返回 `{"status": "ok"}`。
- 页面输入示例改价指令后，能生成结构化计划。
- 未确认前不会执行修改。
- 点击确认后，Mock 菜品价格从 `32.00` 变为 `29.90`。
- 页面状态时间线展示完整执行过程。
- 审计区展示 before/after。

### 9.2 异常验收

- 输入未知门店，返回明确错误。
- 输入未知菜品，返回明确错误。
- 输入低于 1 元价格，拒绝执行。
- 模拟登录失效后，任务进入 `manual_required`。
- 点击 "我已处理，继续执行" 后，任务可以继续完成。

### 9.3 测试验收

必须包含自动化测试:

- 指令解析测试。
- 风险规则测试。
- FakeAdapter 改价测试。
- 工作流状态机测试。
- FastAPI 接口测试。
- 静态页面关键元素测试。

运行:

```powershell
python -m pytest -v
```

应全部通过。

## 10. 技术约束

- 使用 Python + FastAPI + Pydantic + Uvicorn。
- 前端使用单文件静态 HTML/CSS/JS。
- 不引入数据库，第一版用内存状态和 JSONL 审计。
- 不引入 Playwright。
- 不调用真实 LLM。
- 不接真实外卖平台。
- 保留 `.env`，但第一版不依赖真实密钥。
